Database constraints and validation keep individual writes valid. They cannot always detect problems that emerge across records or over time: duplicate customers, orders stuck in an impossible state, missing relationships, or stale derived values.

Data Health lets you express these application-specific rules as **finding classes**. When a rule finds a problem, Data Health creates a persistent **finding record** that your team can review, verify, and resolve.

| Your application | Data Health |
| --- | --- |
| Defines what unhealthy data looks like and how it can be checked or corrected. | Records, deduplicates, and tracks every discovered occurrence. |

Finding classes live in configured directories such as `app/DataHealth`. Data Health discovers them automatically, so each class can focus on the problem it represents instead of registration boilerplate.

## From rule to tracked findings

For example, this finding detects orders that have been paid but are still marked as pending:

```php
use App\Models\Order;
use DataHealth\Contracts\CanDetect;
use DataHealth\Finding;

class PaidOrderMarkedPending extends Finding implements CanDetect
{
    public static function detect(): int
    {
        return Order::query()
            ->whereNotNull('paid_at')
            ->where('status', 'pending')
            ->get()
            ->each(function (Order $order): void {
                self::found($order);
            })
            ->count();
    }
}
```

Run the detector from Artisan:

```bash
php artisan health:detect PaidOrderMarkedPending
```

Omit the finding key to run all discovered detectable findings, or add `--async` to queue detection. See [manual detection](/data-health-docs/guides/detecting-problems/#run-detection-manually) for all command options.

You can also run the detector from application code, a scheduled task, or the optional Filament interface:

```php
PaidOrderMarkedPending::detect();
// 3
```

This run creates or refreshes three persistent finding records—one for each matching order. Data Health can present those records for review and track them until the problems are resolved.

## What a finding can describe

Each finding class can opt into only the capabilities it needs:

- **[Detection](/data-health-docs/guides/detecting-problems/)** finds affected models and records the problem.
- **[Verification](/data-health-docs/guides/verifying-findings/)** checks whether a previously recorded problem still exists.
- **[Resolution](/data-health-docs/guides/resolving-findings/)** performs an application-specific correction.
- **[Scheduling](/data-health-docs/guides/scheduling-and-queues/#schedule-detection)** runs detection from Laravel's scheduler using a cron expression.
- **[Asynchronous execution](/data-health-docs/guides/scheduling-and-queues/#dispatch-detection-to-a-queue)** dispatches scheduled detection through Laravel's queue.
- **[Automatic resolution](/data-health-docs/guides/resolving-findings/#resolve-new-findings-automatically)** attempts to resolve a finding as soon as it is first recorded.

[Attributes](/data-health-docs/reference/attributes-and-contracts/#attributes) can also give a finding a [stable key](/data-health-docs/guides/metadata-and-worklists/#define-a-stable-key), [human-readable descriptions](/data-health-docs/guides/metadata-and-worklists/#describe-a-finding), an [urgency](/data-health-docs/guides/metadata-and-worklists/#assign-an-urgency), and a [worklist](/data-health-docs/guides/metadata-and-worklists/#assign-a-worklist). These values make findings easier to organize and present without coupling the core package to a particular user interface.

## Core package and Filament interface

The Data Health core package owns finding discovery, persistence, lifecycle operations, scheduling, and model integration. It can be used by itself from application code, jobs, commands, APIs, or any interface you build.

The optional [`data-health-filament`](/data-health-docs/filament/overview/) package adds a Filament 5 interface with:

- searchable and filterable finding records;
- verify, resolve, ignore, and reopen actions;
- bulk actions for common workflows;
- a catalogue of registered finding types with manual detection actions;
- overview statistics for the current state of your data; and
- standalone Livewire tables that can be embedded outside a Filament panel.

Both packages use the same finding classes and records, so adding the Filament interface does not change how detection or resolution logic is written.
